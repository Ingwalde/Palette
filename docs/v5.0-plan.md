# PROMPT START

You are working on the **Palette v5.0** release in the `Ingwalde/Palette` repository.

The theme of the release is **"the palette is the product."** The 4.8.x line went almost entirely
into infrastructure — security, CI, observability, accessibility — and the interface fell behind
it. A filtered catalogue cannot be linked to, a single palette has no page of its own, and the
copy on several pages describes the project's own architecture instead of the product. v5.0
closes that gap.

## Repository context

- `frontend-react/` — Vite + React 19 + TypeScript (strict), React Router, TanStack Query,
  **vanilla-extract** for styling (no CSS files at all, only `*.css.ts`), Vitest + Testing
  Library, Playwright + axe-core.
- `backend/` — FastAPI + PostgreSQL (async SQLAlchemy), Redis for rate limiting.
- `docs/` — project documentation; `CHANGELOG.md` and `ROADMAP.md` live at the root.
- Read `frontend-react/README.md` before the first step: it lists every npm script and what each
  of the seven CI jobs does.

## Working rules

1. **Branch**: `release/v5.0`, branched from `main` — the same convention as `release/v4.8.7`
   and `release/v4.9.0`. Push nowhere else.
2. **One step, one commit.** Follow the style of the existing history
   (`feat(home): drive filters from the URL`). Do not fold two steps into one commit.
3. **After every step**, from `frontend-react/`:
   ```bash
   npm run lint && npm run typecheck && npm run test && npm run build && npm run css:orphans
   ```
   A step is not finished until all of that is green.
4. **Visual baselines** (`npm run test:visual`) run in a pinned container and will fail on every
   change that alters rendering — that is expected. Re-record them **narrowly**:
   `npm run test:visual:update -- -g "home"`. Never run `--update` without `-g` until the final
   step: on its own it silently rewrites all nineteen snapshots onto whatever the working tree
   happens to render at that moment.
5. **Language**: all code, comments, interface copy and documentation in English.
6. **Comment style**: comments in this repository explain *why*, not *what*. Match that tone —
   `src/styles/ui.css.ts` and `src/App.tsx` are good samples.
7. **No new runtime dependencies** without asking first. Everything below is achievable with
   what is already in `package.json`.
8. **Tests are written with the code**, not afterwards. Each step has a "Tests" section; treat it
   as the minimum, not the target.
9. If a step turns out to be materially larger than described, or runs into something the plan
   did not anticipate, stop and say so rather than improvising silently.

## Step 1 — Filters live in the URL

**The problem.** `HomePage.tsx:31-33` keeps `search`, `tag` and `sort` in `useState`. A filtered
catalogue therefore cannot be shared, Back does not restore the previous filter, and a reload
discards everything.

**Files**: `src/pages/HomePage.tsx`, `src/pages/homeInteractions.test.tsx`.

**What to do.**

The query string becomes the source of truth: `?q=<search>&tag=<tag>&sort=<az|za>`. Default
values are **omitted** — `/` and `/?sort=default` must not be two different addresses.

The search field stays a controlled local state (`draft`), otherwise it lags on every keystroke.
Synchronisation runs both ways, and each direction needs an equality guard — without it the two
effects feed each other in a loop:

```ts
const [params, setParams] = useSearchParams();
const q = params.get("q") ?? "";
const [draft, setDraft] = useState(q);
const debounced = useDebounce(draft.trim(), 250);

// draft to URL: replace, so typing ten characters does not push ten history entries
useEffect(() => {
  if (debounced === q) return;
  setParams(next => { /* set or delete q */ }, { replace: true });
}, [debounced]);

// URL to draft: Back button, an external link, a reload
useEffect(() => {
  setDraft(prev => (prev.trim() === q ? prev : q));
}, [q]);
```

Clicking a tag or changing the sort is **ordinary navigation** (`replace: false`), so Back
returns the previous filter. Typing is `replace: true`.

Validate what comes in: a `sort` outside `default | az | za` falls back to `default` and is
**stripped from the URL**, so `/?sort=%3Cscript%3E` does not linger in the address bar. A `tag`
that does not exist is left alone — the backend returns an empty list, and the user sees an empty
state naming the tag.

The clear button empties both `draft` and the `q` parameter.

**Interactions that must work when the step is done:**

| Action | Expected result |
| --- | --- |
| Open `/?q=sea&tag=cold&sort=az` | Search field filled, `#cold` chip active, sort A-Z, grid filtered |
| Type "sea" (3 characters) | One API request after 250 ms, **one** new history entry |
| Click a tag, then Back | The previous tag returns and the grid re-renders |
| Reload a filtered page | State fully preserved |
| Copy the address into another tab | Identical view |

**Tests** (`homeInteractions.test.tsx`): render in a `MemoryRouter` with
`initialEntries={["/?q=sea&tag=cold"]}` and assert the input value, the chip's `aria-pressed` and
the API call parameters; click a tag and assert the URL changed; pass an invalid `sort` and
assert the fallback.

**Commit**: `feat(home): drive search, tag and sort from the URL`

## Step 2 — A palette page at `/p/:slug`

**The problem.** The backend has served `GET /api/v1/palettes/{slug}`
(`backend/app/routers/palettes.py:41`) since v3.0, and the frontend calls it **nowhere**. A single
palette does not exist in the interface: it cannot be opened, shared, or given a link preview.
This is the largest gap in the release, and later steps depend on it.

**New files**: `src/pages/PalettePage.tsx`, `src/pages/PalettePage.css.ts`,
`src/pages/PalettePage.test.tsx`.
**Changed**: `src/api/palettes.ts`, `src/api/hooks.ts`, `src/api/queryKeys.ts`, `src/App.tsx`,
`src/components/PaletteCard.tsx`, `src/pages/HomePage.tsx`, `e2e/a11y.spec.ts`,
`e2e/visual/pages.spec.ts`.

**The data layer.**

```ts
// api/palettes.ts
export function getPalette(slug: string): Promise<Palette> {
  return request<Palette>(`/palettes/${encodeURIComponent(slug)}`);
}

// api/queryKeys.ts
palette: (slug: string) => ["palette", slug] as const,

// api/hooks.ts
export function usePalette(slug: string) {
  return useQuery({
    queryKey: queryKeys.palette(slug),
    queryFn: () => getPalette(slug),
    enabled: Boolean(slug),
  });
}
```

Going from a card to the page should be instant, not a loading flash: give `usePalette` an
`initialData` sourced from the already-cached lists via
`queryClient.getQueriesData({ queryKey: ["palettes"] })`. Together with `initialDataUpdatedAt`
that renders immediately and refreshes in the background. When the cache is empty — someone
arriving straight from a link — it falls back to a normal load.

**Route**: `<Route path="p/:slug" element={<PalettePage />} />` inside `<Layout />`, wired through
`lazy` like every route but home.

**Page structure, top to bottom.**

1. **Going back.** A link reading "All palettes". The card passes the current query string through
   router `state`, and the page reads it: `to={`/${location.state?.from ?? ""}`}`. That returns the
   visitor to *their* filtered catalogue rather than a bare home page. With no state — a direct
   visit — it points at `/`.
2. **Heading**: `h1` with the name, the description under it, then the tags, each a `Link` to
   `/?tag=<name>`.
3. **The colour block.** Not the thin strip the card uses: full-width blocks. Each shows its HEX
   **always**, not on hover, with RGB and HSL under it in a smaller size. Clicking copies the HEX
   and raises a toast. The label on top of each colour is black or white depending on the colour's
   luminance — reuse `getRelativeLuminance` from `lib/color.ts` with a 0.5 threshold, or the label
   disappears on light colours.
4. **Action row**: `Save` / `Saved` (the same logic as the card), `Copy all` (every HEX,
   comma-separated), `Copy CSS` (through the existing `generateExportText`), and `Share`, which
   copies `window.location.href` and confirms with a toast.
5. **The contrast matrix.** An N x N table (N is at most 8 per the backend schema) where each cell
   carries the pair's contrast ratio and an `AAA` / `AA` / `—` mark. The diagonal stays empty.
   This is the explanation the card's badge has never given — it does not say which pair it
   compares. Use a real `<table>` with a `<caption>` and `scope` on the headers: this is data, not
   decoration, and a screen reader has to be able to read it. Put the logic in `lib/color.ts` as
   `getContrastMatrix(colors: string[])` with unit tests.
6. **Similar palettes.** Query `usePalettes({ tag: <first tag>, limit: 4 })`, drop the current
   palette, show up to three cards. If there are no tags or no results, do not render the section
   at all — an empty state here is noise.

**The 404 case.** When the query fails with an `ApiError` whose `status` is 404, render an
`EmptyState` titled "Palette not found" with the text "This palette may have been renamed or
removed." and a button back to `/`. Do not show the generic network error: to the user these are
different events.

**Linking card to page.** In `PaletteCard.tsx` only the **title** becomes a link:

```tsx
<h3 className={styles.title}>
  <Link to={`/p/${palette.slug}`} state={{ from: location.search }}>{palette.name}</Link>
</h3>
```

Do **not** wrap the whole card in a `<Link>`: it already contains buttons (the swatches, Save),
and nested interactive elements break both keyboard navigation and screen readers. If a larger
hit area is wanted, stretch the link's `::after` pseudo-element across the card and give the
buttons `position: relative; z-index: 1` so they stay clickable above it.

**"Random palette" moves here.** Today (`HomePage.tsx:54-63`) the button does not show a random
palette: it writes a name into the search box and filters the grid, picking from the already
filtered set. Replace it with `navigate('/p/' + randomSlug)`. When the list is empty, disable the
button.

**Tests.** `PalettePage.test.tsx`: with a mocked API, assert the name, description, tags and the
number of colour blocks; clicking a block calls the clipboard and raises a toast; a 404 response
produces the "Palette not found" state; the back link carries the query string. Plus unit tests
for `getContrastMatrix` in `lib/color.test.ts`.
**E2E**: add `/p/<slug>` to `e2e/a11y.spec.ts` (zero axe violations) and a new `palette-detail`
snapshot to `e2e/visual/pages.spec.ts`.

**Commit**: `feat(palettes): add a shareable palette page at /p/:slug`

## Step 3 — Pagination instead of a silent cap

**The problem.** `HomePage.tsx:50` hardcodes `limit: 100`, and the `total` the backend honestly
returns is read nowhere. Past a hundred palettes the rest vanish with no indication. The export
page has the same flaw at `limit: 200`.

**Files**: `src/api/hooks.ts`, `src/pages/HomePage.tsx`, `src/pages/HomePage.css.ts`,
`src/pages/ExportPage.tsx`.

**What to do.**

Add `usePalettesInfinite` on `useInfiniteQuery`:

```ts
getNextPageParam: (last) =>
  last.offset + last.items.length < last.total ? last.offset + last.limit : undefined,
```

A page is 24 palettes — a multiple of the grid's three columns, so the last row is never ragged.
The query key already contains the filters, so changing a filter resets pagination on its own; no
separate reset logic is needed.

**A "Load more" button, not infinite scroll.** Infinite scroll breaks the footer, works badly from
the keyboard, and damages the CLS this project has already measured. A button is more honest.

Below the grid:
- a counter reading `Showing 24 of 137 palettes`, replacing today's `137 palettes`;
- a `Load more` button, hidden when `hasNextPage` is false, reading `Loading…` and disabled while
  `isFetchingNextPage`.

**Focus handling.** After loading more, focus stays on the button, which is correct — but a screen
reader would not learn that anything appeared. The counter already carries `aria-live="polite"`:
update its text **after** the data lands, and the change from "Showing 24 of 137" to "Showing 48
of 137" is announced. Nothing needs to be focused programmatically.

**Export.** Replace `usePalettes({ limit: 200 })` plus client-side filtering with a server-side
search: `usePalettes({ search: query, limit: 8 })`. The picker then never claims "no palettes
found" merely because the match sat outside the first 200. Delete `matches()` and `defaultSample`
afterwards; for an empty query, fall back to `usePalettes({ limit: 3 })`.

**Tests**: mock the API with `total: 30, limit: 24` and assert the button exists, that clicking it
appends the second page, and that it then disappears; with `total: 10` assert there is no button.

**Commit**: `feat(home): paginate the palette grid instead of capping it at 100`

## Step 4 — Tags ranked by use, not by chance

**The problem.** `pickRandom` in `HomePage.tsx:37-44` reshuffles the chips on every recomputation
of `tags`. That is not only restless to look at, it is a **state bug**: when the selected tag
falls outside the new random ten, the filter disappears from the interface while remaining
applied. The user sees a short list and cannot tell why. Meanwhile the `Tag` type carries a
`count` field that is used nowhere.

**Files**: `src/pages/HomePage.tsx`, `src/pages/HomePage.css.ts`.

**What to do.**

1. Remove `pickRandom` entirely. The chips are the top ten tags by `count`, descending, ties
   broken alphabetically so the order is deterministic across renders.
2. The selected tag is **always** present in the row, even when it falls outside the top ten — if
   it is not there, append it as an eleventh. That condition is what removes the bug.
3. Show the count in the chip: `#cold · 12`. The number makes the filter predictable — you can see
   how many results to expect.
4. A `More tags` button at the end of the row expands the full list (`aria-expanded`,
   `aria-controls`, the container `hidden` until then). Do not build a modal: the existing
   `ModalProvider` only does confirm and prompt, and widening its API for a list of tags is not
   worth it.
5. Mark tags with `kind === "purpose"` (ten of them, seeded on first run) subtly — a different
   border, or a dot before the name. Not with colour: in this application colour means data.

**Tests**: mock `useTags` with varied counts and assert the order; assert a selected tag outside
the top ten is still in the document; assert `More tags` toggles `aria-expanded`.

**Commit**: `feat(home): rank tag chips by usage and keep the active one visible`

## Step 6 — What the card actually does

**The problem.** The card's most prominent action is `Copy name` (`PaletteCard.tsx:99-108`) — it
copies the string "Green Strawberry". A designer needs the hex values or the CSS, not the name.
The contrast badge never says what it compares. And a guest who presses `Save` gets a toast
reading "Log in to save favorites", which is where their intent dies.

**Files**: `src/components/PaletteCard.tsx`, `src/components/PaletteCard.css.ts`,
`src/pages/LoginPage.tsx`, `src/lib/color.ts`.

**What to do.**

1. `Copy name` becomes `Copy all`: copies `palette.colors.join(", ")` and raises
   `4 colors copied`. Drop name-copying entirely; nobody needs it.
2. Give the contrast badge its explanation. Return the pair as well as the ratio from
   `getPaletteContrastStatus` — it already sorts by luminance, so hand back `darkest` and
   `lightest` — and put them in the `title` and in visually hidden text:
   `Good contrast · 4.9:1` plus `Between #0E7490 and #ECEFD4, the darkest and lightest colors.`
   Make the badge itself a link to the contrast matrix on the palette page
   (`/p/<slug>#contrast`).
3. **Save, for a guest**, stops raising a toast into the void and carries the intent instead:
   `navigate("/login", { state: { from: location } })`. In `LoginPage`, after a successful sign-in,
   `navigate(location.state?.from ?? "/", { replace: true })`. Do **not** save the palette
   automatically afterwards: writing to someone's account unasked is bad behaviour. They land back
   on the same card and press it themselves.
4. Keep the `${color} copied` toast, and let it carry the format — after step 7 it reads
   `oklch(…) copied` when that format is selected.

**Tests**: `PaletteCard.test.tsx` — `Copy all` puts every colour on the clipboard; the badge's
accessible text contains both hex values; pressing `Save` while signed out navigates to `/login`
with the state attached.

**Commit**: `feat(card): copy the colors, explain the contrast, respect the save intent`

## Step 7 — Colour formats

**The problem.** HEX is the only format, both on screen and on the clipboard. For a colour tool
that is not enough.

**Files**: `src/lib/color.ts`, `src/lib/color.test.ts`, new
`src/components/ColorFormatContext.tsx`, `src/components/PaletteCard.tsx`,
`src/pages/PalettePage.tsx`, `src/pages/HomePage.tsx`, `src/main.tsx`.

**What to do.**

1. Add pure functions `toRgbString`, `toHslString` and `toOklchString` to `lib/color.ts`, plus a
   `formatColor(hex, format)` dispatcher. The OKLCH conversion is sRGB to linear RGB to OKLab to
   polar coordinates; write it by hand rather than adding a dependency. Rounding: RGB to integers,
   HSL to whole degrees and percentages, OKLCH to three decimals for `L` and `C` and one for `H`.
2. `ColorFormatContext` holds the current format (`hex | rgb | hsl | oklch`) and persists it to
   `localStorage` under `palette:color-format`. Read it in a lazy initialiser
   (`useState(() => …)`) wrapped in try/catch: in some browsers' private mode touching
   `localStorage` throws, and that is no reason to bring the app down. Add the provider in
   `main.tsx` alongside the others.
3. The switch goes in the home toolbar next to the sort control, as a `CustomSelect` — the
   component already exists, which is less new code and consistent with its neighbour.
4. **A shortcut worth knowing**: the swatch label is drawn with `content: attr(data-color)`
   (`PaletteCard.css.ts:78`). Putting the **formatted** string into `data-color` therefore needs no
   CSS change at all. But the button's `aria-label` must carry the same string as the label, or
   the screen reader and the eye disagree.
5. Copying always yields the current format.

**Tests**: unit tests for the conversions against known values (`#000000`, `#ffffff`, `#ff0000`,
`#3b6fd4`); a test that changing the format changes both the label and the copied string; a test
that a throwing `localStorage` does not break the render.

**Commit**: `feat(color): switch between HEX, RGB, HSL and OKLCH`

## Step 8 — Dark theme

**The problem.** The project does not mention `prefers-color-scheme` anywhere. For a colour tool
that is a conspicuous gap: colours read differently against a dark ground, and half the audience
works that way.

This is the riskiest step in the release — it touches every `*.css.ts`. Do it **after** steps 1
through 7 so the baselines are not re-recorded twice.

**Files**: `src/styles/theme.css.ts`, `src/styles/global.css.ts`, every `*.css.ts` holding a
hardcoded colour (listed below), `index.html`, new `public/theme-init.js`, new
`src/components/ThemeToggle.tsx`, and `frontend-react/nginx.conf.template` (verify the CSP).

**What to do.**

1. **Extend the token contract** in `theme.css.ts`. Two are missing:
   - `color.onPrimary` — text on a `primary` background. Today that is a hardcoded `#fff` in eight
     places; in dark mode `primary` becomes light and white text on it disappears.
   - `color.focus` — a dedicated focus-ring colour (see step 9).
   `shadow.soft` also needs a dark variant: a black shadow on a dark ground is invisible, and only
   raised opacity or a thin light border does the job.

2. **Replace every hardcoded light value with a token.** This is the full list found by grep — work
   through each:

   | File | Lines |
   | --- | --- |
   | `styles/ui.css.ts` | 40, 50, 350 (`#fff` to `onPrimary`) |
   | `styles/global.css.ts` | 117 (`::selection`) |
   | `styles/auth.css.ts` | 74 |
   | `components/Layout.css.ts` | 19, 52, 164, 183, 273 |
   | `components/PaletteCard.css.ts` | 18, 90 |
   | `components/EmptyState.css.ts` | 20 |
   | `components/CustomSelect.css.ts` | 32, 102, 144 |
   | `components/toast/Toast.css.ts` | 32 |
   | `pages/HomePage.css.ts` | 38, 93, 98 |
   | `pages/ExportPage.css.ts` | 24, 68, 111 |
   | `pages/ChangelogPage.css.ts` | 14, 25 |
   | `pages/AdminPage.css.ts` | 12, 91 |
   | `pages/ProfilePage.css.ts` | 26, 47 |

   The translucent `rgba(255, 250, 242, 0.78)` values are "glass surfaces". Give them their own
   token, `color.surfaceGlass`, rather than substituting `surface`: the transparency is load-
   bearing, since the background gradient shows through the cards.

3. **Declare the dark theme.** `createGlobalTheme` cannot be nested inside a media query, so it
   takes two declarations:

   ```ts
   const dark = { /* values */ };
   createGlobalTheme("[data-theme='dark']", vars, dark);           // an explicit choice
   globalStyle(":root:not([data-theme='light'])", {                 // the system preference
     "@media": { "(prefers-color-scheme: dark)": { vars: flatten(dark) } },
   });
   ```
   `globalStyle` accepts a `vars` key, and that is how contract values get overridden inside a
   media query. The `:not([data-theme='light'])` selector is what lets an explicitly chosen light
   theme win over a dark system preference.

4. **Dark palette values** — a starting point; verify contrast once applied:
   ```
   bg            #141312
   surface       #1c1a18
   surfaceGlass  rgba(28, 26, 24, 0.78)
   surfaceStrong #262320
   text          #f2ede6
   muted         #a89e93
   border        rgba(242, 237, 230, 0.14)
   primary       #f2ede6
   onPrimary     #1c1a18
   primarySoft   #33302c
   danger        #e0736f
   success       #6fbf7a
   ```
   The radial gradient on `body` (`global.css.ts:55`) needs overriding too — a warm light bloom
   over a dark ground looks muddy.

5. **The toggle.** Three states — `System / Light / Dark` — in the header beside the navigation.
   Persist to `localStorage` under `palette:theme`; the `system` value **deletes** the key rather
   than writing the string "system", so a later change of default is not stuck behind it.

6. **The flash of light theme** before React starts is removed by a script in `<head>` that sets
   `data-theme` before the first paint. **Watch the CSP**: `nginx.conf.template:30` serves
   `script-src 'self'` with no `'unsafe-inline'`, so an inline `<script>` is blocked in production
   — and not in dev, so the bug will not show up locally. Ship it as a **separate file**,
   `public/theme-init.js`, included as `<script src="/theme-init.js"></script>` in `<head>`,
   synchronously, ahead of the bundle. The CSP itself needs no change.

7. `index.html`: add `<meta name="color-scheme" content="light dark">` and update the stale
   `<meta name="description">`, which still says "v4.8.x".

**Tests**: a unit test for the theme-selection reducer (system/light/dark to attribute); E2E —
run axe in dark mode (`page.emulateMedia({ colorScheme: 'dark' })`) and add a dark home-page
snapshot to the visual baselines.

**Commit**: `feat(theme): add a dark theme with a system-aware toggle`

## Step 9 — The accessibility debt that has piled up

**Files**: `src/styles/global.css.ts`, `src/components/toast/*`, `src/components/Layout.css.ts`,
`src/pages/FavoritesPage.tsx`, `src/components/EmptyState.css.ts`, new
`src/components/PaletteCardSkeleton.tsx`.

Each item is small; together they are what "feels finished" is made of.

1. **`prefers-reduced-motion` is not covered everywhere.** Cards, modals and empty states respect
   it; `html { scroll-behavior: smooth }` (`global.css.ts:46-48`), the toast animation
   (`Toast.css.ts`) and the navigation indicator (`Layout.css.ts:98`) do not. Wrap all three.
   `EmptyState.css.ts:49-54` carries a comment saying its button was left out deliberately, "as
   its own decision rather than a silent change" — this is that decision; finish it.

2. **Toasts.** They vanish after exactly 2.6 s with no way to hold them
   (`ToastProvider.tsx:33`), which conflicts with WCAG 2.2.1. Change to:
   - pause the timer on `mouseenter` and `focusin`, resume on leave;
   - errors last 6 s, informational toasts 3 s;
   - move errors into a **separate** container with `role="alert"` / `aria-live="assertive"`,
     leaving informational ones polite;
   - drop `aria-atomic="true"` from the container: with several toasts a screen reader re-reads
     the whole stack instead of the new message;
   - give every toast a dismiss button (`aria-label="Dismiss"`).

3. **The focus ring.** `global.css.ts:88-91` draws `2px solid var(--color-primary)` — very nearly
   black. On the active navigation tab and on a primary button, both dark themselves, it is
   invisible. Make it two-layer: `outline: 2px solid var(--color-focus)` plus
   `box-shadow: 0 0 0 4px var(--color-focus-halo)`, where `focus` contrasts with the surface and
   the halo is translucent. Check it against the active tab, a primary button, a swatch, a tag
   chip and an input.

4. **`Clear favorites` fires without confirmation** (`FavoritesPage.tsx:44-50`). The project
   already has `useModal().confirm`, and both Admin and "log out everywhere" use it. Add:
   title `Clear all favorites?`, body `This removes all N saved palettes from your account. It
   can't be undone.`, `confirmLabel: "Clear favorites"`.

5. **Skeletons instead of a loading sentence.** Today the whole grid shows
   `EmptyState "Loading palettes"`, and the layout jumps when the data lands. Build
   `PaletteCardSkeleton` at the card's height, render six, mark the container `aria-hidden="true"`
   and put a visually hidden `<p role="status">Loading palettes…</p>` beside it. Disable the
   shimmer under `prefers-reduced-motion`.

**Tests**: a toast does not disappear while hovered; `Clear favorites` calls nothing without
confirmation; skeletons disappear once data arrives. The E2E axe suite must stay at zero
violations.

**Commit**: `fix(a11y): pausable toasts, a visible focus ring, and a guarded destructive action`

## Step 11 — Colour-vision simulation *(optional; can slip to 5.1)*

The most interesting addition in the release and the one most native to this product: a switch
that shows a palette as someone with protanopia, deuteranopia or tritanopia sees it.

**Implementation.** Compute nothing in JS: declare three `<filter>` elements with `feColorMatrix`
in a hidden SVG (its own component, mounted in `Layout`) and apply `filter: url(#deuteranopia)` to
the swatch container. Use the standard Brettel/Viénot coefficients and put them in
`src/lib/colorVision.ts` with a comment citing the source.

**Interaction.** The control sits in the toolbar beside the colour format, defaulting to `None`.
While a filter is on, a line appears above the grid: `Simulating deuteranopia. Copied values are
unchanged.` That line is essential — without it a user concludes the data itself is broken.
Copying always yields the original colour.

Keep the state in the same context as the colour format. Do **not** persist it: this is an
inspection mode, not a preference, and it must not stick.

**Commit**: `feat(a11y): simulate color vision deficiency on the palette grid`

## Deliberately out of scope

Do not do these in this release even if they feel adjacent — record them in `ROADMAP.md` as
deferred:

- **Colour search** ("find palettes near `#3B6FD4`"). Done honestly it is a OKLab delta-E query on
  the backend with an index; a client-side version over the first 500 palettes will start lying as
  the database grows. That is its own release, with a migration.
- **Keyboard shortcuts** (`/` for search, `r` for random, `?` for help). Cheap, but it needs a
  careful global handler that stays silent inside input fields, plus a help dialog of its own.
- **Recently viewed**, in `localStorage`.
- **A palette preview inside a mock UI** — a fake button, card and chart painted in the palette's
  colours.
- **An OG image for the palette page.** It needs server-side rendering or a dedicated endpoint; an
  SPA will not hand meta tags to a crawler on its own. Along with the rest of SEO, that is
  separate work.
