# PROMPT START

You are working on the **Palette v5.0** release in the `Ingwalde/Palette` repository.

## Theme

**"Palette becomes a community."** The 4.8/4.9 line went into infrastructure — security, CI,
observability, accessibility — and the interface fell behind it. v5.0 has two layers, built in
order:

1. **The palette is the product** (UI foundation). A filtered catalogue you can link to, a page
   per palette, real formats, a dark theme. This was the original v5.0 plan and still holds.
2. **The community layer** on top: users create palettes, keep them private or publish them,
   browse a public feed, fork each other's work, send palettes directly, and import colours from
   an image, a Figma file, or a Pinterest board.

This is roughly four releases of scope under one banner. It ships as **stacked PRs behind feature
flags**, never one giant merge. Each user-facing pillar (gallery, direct-send, figma-import,
pinterest-import) sits behind a flag so a half-built pillar can land on `main` switched off.

## Repository context

- `frontend-react/` — Vite + React 19 + TypeScript (strict), React Router, TanStack Query,
  **vanilla-extract** for styling (no CSS files at all, only `*.css.ts`), Vitest + Testing
  Library, Playwright + axe-core.
- `backend/` — FastAPI + PostgreSQL (async SQLAlchemy 2.0), Alembic migrations, Redis for rate
  limiting, Argon2id, httpOnly-cookie auth with double-submit CSRF, RFC 7807 problem+json.
- `docs/` — project documentation; `CHANGELOG.md` and `ROADMAP.md` live at the root.
- Read `frontend-react/README.md` before the first step: it lists every npm script and what each
  CI job does. Read the root `.claude/CLAUDE.md` for the security invariants and the version-bump
  checklist — both are load-bearing here.

## Working rules

1. **Branch**: `release/v5.0` off `main`. Feature work branches off `release/v5.0`
   (`feat/v5.0-<pillar>-<step>`) and PRs back into it; only the final integrated `release/v5.0`
   merges to `main`. Push nowhere else.
2. **One step, one commit.** Match the existing history voice
   (`feat(home): drive filters from the URL`). Author is the owner only — no co-author trailers.
3. **Docker is the gate. Nothing merges until it is green in Docker**, not merely on the host:
   ```bash
   # frontend, from frontend-react/
   npm run lint && npm run typecheck && npm run test && npm run build && npm run css:orphans
   # e2e + visual in the pinned container (host-native runs produce *-win32.png and lie)
   npm run test:visual:docker
   # backend, from repo root
   docker compose --profile test run --rm tests
   ```
   A step is not finished until all of that passes. The full stack must also come up clean:
   `docker compose up --build` with a real `SECRET_KEY`.
4. **Visual baselines** are re-recorded **narrowly** per step
   (`npm run test:visual:docker:update -- -g "home"`) and **in full only at the release step**.
   `--update` without `-g` silently rebases all snapshots onto whatever the tree renders.
5. **Migrations** use Alembic. CI runs `alembic check` for model/migration drift — every model
   change ships with its migration in the same commit, or that job fails.
6. **Security invariants do not regress** (see CLAUDE.md). New surfaces inherit them: every new
   mutation is CSRF-protected and rate-limited; OAuth tokens for Figma/Pinterest are stored
   server-side, encrypted, never exposed to JS; user-supplied content (palette names, image URLs)
   is validated in Pydantic; timestamps stay tz-aware UTC.
7. **No new runtime dependencies without asking first.** The colour maths (quantisation, OKLCH)
   is written by hand. OAuth uses `httpx` (already present). Image decoding for the extractor is
   done client-side with `<canvas>` — no backend image library.
8. **Language**: all code, comments, interface copy and docs in English. Comments explain *why*,
   not *what* (`src/styles/ui.css.ts`, `src/App.tsx` are good samples).
9. **Tests are written with the code.** Each step's "Tests" section is the minimum, not the target.
10. If a step is materially larger than described, **stop and say so** rather than improvising.

## Locked decisions

These were decided before the plan was written. Do not re-open them silently.

- **Ownership.** `Palette.owner_id` is nullable. `null` = a system/seed palette (the current
  admin-seeded catalogue). A user-created palette carries its author's id.
- **Visibility.** `private on create → public on publish`. Two states only: `private`
  (owner-only) and `public` (in the feed, shareable). No `unlisted` tier in v5.0 — a shared link
  implies public. `published_at` records the transition.
- **Home = community feed.** The home grid reads **public** palettes, with three sorts:
  **new** (published_at desc), **popular** (by favourite/fork counters), **curated** (an
  admin `is_featured` flag). Sort lives in the URL (`?sort=new|popular|curated`, default `new`).
  The old admin catalogue is not a separate page — seed palettes are simply public and
  `is_featured`, so the feed is never empty on day one (cold-start).
- **Direct send = send a copy.** "A sends B a palette" **forks the palette into B's account**
  (private) and notifies B. No access-control-list, no shared ownership — the recipient gets
  their own editable copy with `forked_from_id` set. This avoids an ACL system for a feature with
  modest ROI.
- **Moderation is mandatory** the moment anything is public: a `report` flow, an admin review
  queue, and a takedown that sets `Palette.status = removed`. Creation and reporting are
  rate-limited.
- **URL identity — CONFIRM.** Default chosen: keep **`/p/:slug`**, with `slug` **globally unique**
  by appending a short suffix on collision (`sunset`, `sunset-a1`, …). This preserves the existing
  `GET /api/v1/palettes/{slug}` route and the palette page from Phase 1, and keeps a clean share
  URL. The alternative (`/u/:user/:slug`) is rejected as noisier. Confirm before Phase 2.
- **Canva is out.** Its Connect API exposes no colour/brand-kit endpoint; the only path was
  export→image, which the image extractor already covers generically.
- **Imports.** An **image→palette extractor** is the core (client-side canvas quantisation). It is
  the engine under Pinterest (a pin has no palette, only an image) and doubles as a generic
  upload/URL import. **Figma** import uses OAuth to read a file's styles for exact hex.
  **Pinterest** import uses OAuth to fetch a board/pins and runs their images through the
  extractor — behind a flag, because Pinterest gates non-trial API access behind app review.
- **Feature flags.** `feature_community`, `feature_direct_send`, `feature_import_figma`,
  `feature_import_pinterest` — server-provided config the SPA reads once, so partial pillars land
  dark on `main`.

## Data model (the shared core — build once, in Phase 2)

All three community pillars sit on the same additions. One Alembic migration introduces them.

**`palettes`** — new columns:
- `owner_id INT NULL REFERENCES users(id) ON DELETE CASCADE` — null for seed/system palettes.
- `visibility` — enum `private | public`, default `private`.
- `published_at TIMESTAMPTZ NULL` — set when first made public.
- `forked_from_id INT NULL REFERENCES palettes(id) ON DELETE SET NULL` — lineage for fork/send.
- `status` — enum `active | removed`, default `active` (moderation takedown).
- `is_featured BOOL NOT NULL DEFAULT false` — the "curated" sort / cold-start.
- `favorites_count INT NOT NULL DEFAULT 0`, `forks_count INT NOT NULL DEFAULT 0` — denormalised
  counters for the "popular" sort, updated in the same transaction as the favourite/fork. A
  live `COUNT(*)` per feed request does not scale; the counters do. Backfill on migration.
- Indexes: `(visibility, status, published_at DESC)` for the feed; `(owner_id)` for "your
  palettes"; keep the existing GIN/trigram search index.

**`reports`** — new table:
- `id`, `palette_id` (FK), `reporter_id` (FK, nullable for future anonymous), `reason` (short
  enum + free text, both length-capped), `status` enum `open | actioned | dismissed`,
  `created_at`. Unique `(palette_id, reporter_id)` so one user cannot spam-report one palette.

**`notifications`** — new table (for direct-send; behind `feature_direct_send`):
- `id`, `user_id` (recipient FK), `kind` enum (`palette_received`, extensible), `payload` JSONB
  (sender username, palette slug), `read_at TIMESTAMPTZ NULL`, `created_at`.

**`oauth_tokens`** — new table (for Figma/Pinterest import):
- `id`, `user_id` (FK), `provider` enum (`figma | pinterest`), encrypted `access_token` /
  `refresh_token`, `expires_at`, `scope`, `created_at`. Tokens are encrypted at rest (reuse the
  SOPS/age posture for the key, or a Fernet key from `SECRET_KEY`-derived material) and never
  leave the backend. One row per `(user_id, provider)`.

Authorisation rule that every write in Phase 2+ obeys: **a palette may be read by anyone if it is
`public` + `active`, or by its owner always; it may be written only by its owner (or an admin).**
The seed palettes (`owner_id IS NULL`) remain admin-only to edit.

# Phase 1 — UI foundation ("the palette is the product")

No data-model change yet. This is the original v5.0 plan, with two adjustments so the home page
and the card are **designed for the community destination** and are not rebuilt in Phase 3:
the card gets an owner/attribution slot (empty for seed palettes now, filled later), and the home
grid is built as a feed shell whose data source swaps from "all palettes" to "public palettes" in
Phase 3 without a layout change.

## Step 1.1 — Filters live in the URL

**Problem.** `HomePage.tsx` keeps `search`, `tag`, `sort` in `useState`. A filtered catalogue
cannot be shared, Back does not restore it, a reload discards it.

**Files**: `src/pages/HomePage.tsx`, `src/pages/homeInteractions.test.tsx`.

The query string is the source of truth: `?q=<search>&tag=<tag>&sort=<sort>`. Defaults are
**omitted** (`/` and `/?sort=new` are not two addresses). Search stays a controlled `draft` with a
250 ms debounce; sync runs both ways, each direction guarded by an equality check or the two
effects loop. Typing is `replace: true` (ten keystrokes ≠ ten history entries); clicking a tag or
changing sort is ordinary navigation (`replace: false`) so Back works. Validate input: an unknown
`sort` falls back to the default and is stripped from the URL; an unknown `tag` is left alone (the
backend returns an empty list and the empty state names it).

**Tests**: render in `MemoryRouter` with `initialEntries={["/?q=sea&tag=cold"]}`; assert input
value, chip `aria-pressed`, API params; click a tag and assert the URL; pass an invalid `sort` and
assert the fallback.

**Commit**: `feat(home): drive search, tag and sort from the URL`

## Step 1.2 — A palette page at `/p/:slug`

**Problem.** The backend has served `GET /api/v1/palettes/{slug}` since v3.0; the frontend calls
it nowhere. A single palette cannot be opened, shared, or link-previewed. This is the backbone of
the release — the page every later "Share / Fork / Send" action targets.

**New**: `src/pages/PalettePage.tsx` + `.css.ts` + `.test.tsx`.
**Changed**: `src/api/palettes.ts`, `hooks.ts`, `queryKeys.ts`, `App.tsx`, `PaletteCard.tsx`,
`HomePage.tsx`, `e2e/a11y.spec.ts`, `e2e/visual/pages.spec.ts`.

Data layer: `getPalette(slug)`, `queryKeys.palette(slug)`, `usePalette(slug)` with `initialData`
sourced from cached lists (`queryClient.getQueriesData({ queryKey: ["palettes"] })`) so a card→page
transition is instant, falling back to a normal load on a cold arrival. Route
`<Route path="p/:slug" element={<PalettePage/>}/>` inside `<Layout/>`, lazy.

Page top-to-bottom: (1) an "All palettes" back link that reads the query string the card passed
through router `state`, returning the visitor to *their* filter; (2) `h1` name + description +
tags as links to `/?tag=<name>`; (3) **an owner byline slot** — for a seed palette render nothing;
this is where Phase 3 puts "by <user>"; (4) full-width colour blocks, each showing HEX always
(plus RGB/HSL smaller), click-to-copy with a toast, label black/white by luminance
(`getRelativeLuminance`, 0.5 threshold); (5) action row `Save`/`Saved`, `Copy all`, `Copy CSS`
(via `generateExportText`), `Share` (copies `location.href` + toast); (6) **the contrast matrix**
— a real `<table>` with `<caption>` and `scope`, N×N ratios with AAA/AA/— marks, diagonal empty;
put `getContrastMatrix(colors)` in `lib/color.ts` with unit tests; (7) "Similar palettes" —
`usePalettes({ tag: firstTag, limit: 4 })` minus the current one, hidden if none.

404: an `ApiError` with `status === 404` renders an `EmptyState` "Palette not found", not the
generic network error. Card→page link: only the **title** is a `<Link to={`/p/${slug}`}
state={{ from: location.search }}>`; do not wrap the whole card (it holds buttons). "Random
palette" becomes `navigate('/p/' + randomSlug)`, disabled when the list is empty.

**Tests**: name/description/tags/colour-count; click copies + toast; 404 state; back link carries
the query string; unit tests for `getContrastMatrix`. **E2E**: `/p/<slug>` in `a11y.spec.ts` (zero
violations) + a `palette-detail` visual snapshot.

**Commit**: `feat(palettes): add a shareable palette page at /p/:slug`

## Step 1.3 — Pagination instead of a silent cap

**Problem.** `HomePage` hardcodes `limit: 100` and ignores the honest `total`; past 100 palettes
the rest vanish. Export has the same flaw at 200.

`usePalettesInfinite` on `useInfiniteQuery`, page size **24** (a multiple of the 3-column grid).
The query key already holds the filters, so a filter change resets pagination on its own. A
**"Load more" button, not infinite scroll** (infinite scroll breaks the footer, the keyboard, and
CLS). Below the grid: a counter `Showing 24 of 137 palettes` (with `aria-live="polite"`, updated
after the data lands so a screen reader hears it) and a `Load more` button hidden when
`!hasNextPage`, disabled + `Loading…` while fetching. Export: replace `usePalettes({ limit: 200 })`
+ client filtering with server-side `usePalettes({ search: query, limit: 8 })`; delete `matches()`
and `defaultSample`.

**Tests**: `total: 30, limit: 24` → button appends page two then disappears; `total: 10` → no
button.

**Commit**: `feat(home): paginate the palette grid instead of capping it at 100`

## Step 1.4 — Tags ranked by use, not by chance

**Problem.** `pickRandom` reshuffles chips every recompute — restless, and a **state bug**: when
the active tag falls outside the random ten, the filter vanishes from the UI while still applied.
`Tag.count` is unused.

Remove `pickRandom`. Chips are the top ten tags by `count` desc, ties alphabetical (deterministic).
The **selected tag is always present**, appended as an eleventh if outside the top ten — this
removes the bug. Show the count: `#cold · 12`. A `More tags` button expands the full list
(`aria-expanded`/`aria-controls`, container `hidden` until then) — no modal. Mark `kind==="purpose"`
tags subtly (border/dot, **not colour** — colour means data here).

**Tests**: order by count; selected out-of-top-ten still present; `More tags` toggles
`aria-expanded`.

**Commit**: `feat(home): rank tag chips by usage and keep the active one visible`

## Step 1.5 — The home hero, sized for the product

**Problem.** The global `h1` `clamp(2.4rem, 6vw, 5rem)` eats the first screen — no palette visible
at 1280×800 on a site about palettes. The hero lead is a release note, not product copy.

`h1`: `clamp(2.2rem, 4.5vw, 3.6rem)` (global; every baseline re-records). Hero copy: eyebrow
`Curated color palettes` (version moves to the footer only); `h1`
`Find the right colors for your space`; lead `Search by name, tag or color. Check contrast before
you commit. Export to CSS, JSON or PNG, and save what you like to your account.`; a small
`What's new in v5.0` link to `/changelog`. Replace the four hardcoded preview rectangles with a
**real** featured palette (first from the API), linking to its page (`aria-hidden` off, an
`aria-label`, a same-size placeholder while loading). Clear developer vocabulary out of the
interface — `Backend data`→`Browse`, `Available palettes`→`All palettes`, the "start the stack"
error → a human one with a `Try again` button calling `refetch()`, the Favorites and Export leads
rewritten (see the table in git history of the old plan). Walk every page for the same register.

**Note:** in Phase 3 this home page becomes the community feed. Build the hero and the section
heading so the grid below can swap its data source (all → public) and gain the new/popular/curated
sort control without a layout change.

**Tests**: update copy assertions; add one that `Try again` refetches.

**Commit**: `feat(home): rewrite the hero around the product, not the release`

## Step 1.6 — What the card actually does

**Problem.** The card's loudest action is `Copy name` — it copies "Green Strawberry". The contrast
badge never says what it compares. A guest pressing `Save` gets a dead-end toast.

`Copy name`→`Copy all` (`colors.join(", ")`, toast `4 colors copied`); drop name-copying. Give the
contrast badge its pair: return `darkest`/`lightest` from `getPaletteContrastStatus`, put them in
the `title` and visually-hidden text, make the badge a link to `/p/<slug>#contrast`. **Guest
Save** carries intent instead of dying: `navigate("/login", { state: { from: location } })`, and
`LoginPage` returns to `state.from` after sign-in (do **not** auto-save — writing to an account
unasked is bad). **Add the owner byline slot to the card** — empty for seed palettes now, `by
<user>` in Phase 3.

**Tests**: `Copy all` clipboard; badge accessible text has both hex; guest `Save` navigates to
`/login` with state.

**Commit**: `feat(card): copy the colors, explain the contrast, respect the save intent`

## Step 1.7 — Colour formats

**Problem.** HEX is the only format, on screen and clipboard. Not enough for a colour tool.

Pure `toRgbString`/`toHslString`/`toOklchString` + a `formatColor(hex, format)` dispatcher in
`lib/color.ts` (OKLCH by hand: sRGB→linear→OKLab→polar; RGB integers, HSL whole units, OKLCH 3dp
L/C, 1dp H). A `ColorFormatContext` (`hex|rgb|hsl|oklch`) persisted to `localStorage` under
`palette:color-format` via a try/catch lazy initialiser (private mode throws). The switch is a
`CustomSelect` in the home toolbar beside sort. The swatch label already uses
`content: attr(data-color)`, so putting the formatted string in `data-color` needs no CSS change —
but keep the button `aria-label` in step with the label. Copying yields the current format.

**Tests**: conversions against known values; format change updates label + clipboard; a throwing
`localStorage` does not break render.

**Commit**: `feat(color): switch between HEX, RGB, HSL and OKLCH`

# Phase 2 — Community core (ownership, create, private/publish)

Backend model + the ability for a user to make and hold their own palettes. Nothing is public yet,
so no moderation surface yet. **Confirm the URL-identity decision before starting.**

## Step 2.1 — The data-model migration

Add every column and table from the **Data model** section in one Alembic migration, with the
backfill (seed palettes → `owner_id NULL`, `visibility public`, `is_featured true`,
`published_at = created_at`; counters computed from existing favourites). Update the SQLAlchemy
models (`Mapped` typed) and the `TagRead`/`PaletteRead` schemas. `alembic check` must pass.

**Tests**: a migration up/down round-trip in the test DB; model tests for the new defaults.

**Commit**: `feat(model): palette ownership, visibility, moderation and counters`

## Step 2.2 — Owner-scoped palette CRUD

Move create/update/delete off admin-only onto **owner-or-admin**. `POST /api/v1/palettes` sets
`owner_id = current_user`, `visibility = private`. `PATCH`/`DELETE` authorise the owner (or admin).
Reads: public+active to anyone, own always, others' private → 404 (not 403 — do not reveal
existence). Rate-limit creation (e.g. `20/hour`) and validate everything in Pydantic (name length,
≤8 colours, tag rules already exist). CSRF on all of it (existing middleware covers cookie auth).

**Tests** (backend): owner can edit own, cannot edit another's (404), guest cannot create,
rate-limit trips, a private palette is 404 to a stranger.

**Commit**: `feat(palettes): owner-scoped create, edit and delete`

## Step 2.3 — The palette editor for users

Reuse the admin colour-row editor components (pickers, hex rows, tag chips) in a user-facing
`Create palette` / `Edit palette` flow reachable from the header and from "Your palettes". Not the
admin page — a clean route (`/palettes/new`, `/p/:slug/edit`) gated by auth. Optimistic where it
already is; invalidate the right query keys.

**Tests** (frontend): create submits the right payload; edit pre-fills; validation errors surface.

**Commit**: `feat(palettes): a create/edit flow for signed-in users`

## Step 2.4 — "Your palettes" and Publish

A `/palettes/mine` page listing the user's own palettes with their visibility state and a
**Publish** / **Make private** toggle (`PATCH` sets `visibility`, stamps/clears `published_at`).
Private palettes never appear in any public query. The profile page links here.

**Tests**: mine lists only own; publish flips visibility and stamps `published_at`; a published
palette becomes readable by a stranger, a re-privatised one 404s again.

**Commit**: `feat(palettes): a "your palettes" collection with publish control`

# Phase 3 — The community layer (feed, fork, moderation, send)

Everything here is behind `feature_community` (and `feature_direct_send` for the last step).

## Step 3.1 — Home is the community feed

Swap the home grid's data source from "all palettes" to **public + active** palettes, with the
three sorts in the URL (`?sort=new|popular|curated`, default `new`). `new` = `published_at desc`,
`popular` = `favorites_count + forks_count` weighting, `curated` = `is_featured` desc then new. The
sort control is a `CustomSelect` beside the existing filters. Seed palettes are public + featured,
so `curated` is the pleasant default-feeling view and the feed is never empty. Fill the **owner
byline** on card and page (`by <user>`, linking to a future profile; for seed palettes, "Palette").

**Tests**: each sort orders correctly against a mocked API; private palettes never appear; byline
renders for owned and seed palettes.

**Commit**: `feat(community): turn the home grid into a public feed with new/popular/curated`

## Step 3.2 — Fork / remix

On any public palette page, a **Fork** action copies it into the actor's account as `private` with
`forked_from_id` set, bumps the source's `forks_count`, and navigates to the new copy's editor. The
page shows lineage ("Forked from <name> by <user>") when `forked_from_id` is set. Guests forking go
through the `/login` intent path from Step 1.6.

**Tests** (backend): fork creates an owned private copy, sets lineage, increments the counter;
(frontend) the button navigates to the copy; lineage renders.

**Commit**: `feat(community): fork a public palette into your own collection`

## Step 3.3 — Moderation

`POST /api/v1/palettes/{slug}/report` (rate-limited, unique per reporter) opens a `report`. An
admin **review queue** page lists open reports with the palette and reason; actioning sets
`Palette.status = removed` (it drops out of every public query and returns 404/"removed" to
non-owners) and marks the report `actioned`; dismissing marks it `dismissed`. A removed palette is
not hard-deleted — the owner sees a "removed by moderation" state on their own copy.

**Tests**: report is rate-limited and deduped; actioning hides the palette from the feed and from
strangers; the admin queue lists and resolves.

**Commit**: `feat(moderation): report flow and an admin review queue`

## Step 3.4 — Direct send *(behind `feature_direct_send`; lowest priority)*

`POST /api/v1/palettes/{slug}/send` with a recipient username **forks the palette into the
recipient's account** (private, `forked_from_id` set) and writes a `notification`. A header bell
reads unread notifications (`GET /notifications`, `PATCH .../read`). Rate-limit sends hard (spam
vector). Recipient lookup by exact username only — no directory, no enumeration.

**Tests**: send creates a private copy for the recipient + a notification; rate-limit trips;
unknown recipient is a clean error without revealing which usernames exist.

**Commit**: `feat(community): send a palette to another user`

# Phase 4 — Import

The extractor is the engine; the two OAuth providers feed it (Pinterest) or bypass it (Figma).

## Step 4.1 — Image → palette extractor (core)

A client-side extractor: `Upload image` or `Paste image URL` → decode on a `<canvas>` →
**median-cut quantisation** (written by hand in `lib/quantize.ts`, unit-tested) → N dominant
colours → an editable draft that saves as a normal palette. A pasted **URL** may be cross-origin;
fetching its pixels in the browser hits CORS. Handle it with a small **backend proxy**
(`GET /api/v1/import/fetch?url=` — allowlist schemes, cap size, strip to image bytes, rate-limit)
rather than a client fetch. Upload path needs no proxy.

**Tests**: quantiser against a known image buffer; the panel produces a draft; the proxy rejects
non-image and oversized URLs.

**Commit**: `feat(import): extract a palette from an uploaded or linked image`

## Step 4.2 — Figma import *(behind `feature_import_figma`)*

Figma **OAuth2** (read scope). Store the token in `oauth_tokens` (encrypted). The user pastes a
file URL / key; the backend calls the Figma REST **GET** styles + nodes, pulls the fill colours of
the file's paint styles, and returns exact hex as a draft. Read is not Enterprise-gated (write is —
which is why this is import-only). Token refresh handled server-side; the token never reaches JS.

**Tests**: with the Figma API mocked, styles map to a draft; an expired token triggers refresh; a
file with no styles gives a clear empty state.

**Commit**: `feat(import): pull exact colors from a Figma file`

## Step 4.3 — Pinterest import *(behind `feature_import_pinterest`)*

Pinterest **OAuth2**. The user picks a board / pin; the backend fetches the pin image URLs and runs
them through the **extractor** from 4.1 (a pin carries an image, not a palette). Behind a flag
because production Pinterest API access requires **app review** — trial access covers development,
and the flag lets the release ship without it. Same encrypted-token posture as Figma.

**Tests**: with the Pinterest API mocked, a pin image yields a draft via the extractor; missing
scope / unapproved app degrades to a clear message, not a crash.

**Commit**: `feat(import): build a palette from a Pinterest pin`

# Phase 5 — UI polish (after the community UI has settled)

Done late so the heavy-stylesheet work is not re-recorded twice.

## Step 5.1 — Dark theme

The riskiest step — it touches every `*.css.ts`. Extend the token contract (`color.onPrimary`,
`color.focus`, a dark `shadow.soft`, a `color.surfaceGlass` for the load-bearing translucency).

**Tests**: theme-reducer unit test; axe in dark mode (`emulateMedia({ colorScheme: 'dark' })`);
